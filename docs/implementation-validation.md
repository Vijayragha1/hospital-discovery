PDF reconciliation coalesces an OCR line only when exact ordered NFC words match a mutually unique native line at corresponding word positions on the same original page. Real repeats at other positions survive; conflicts, merged columns and unsupported geometry retain separate observations. Residual OCR fragments stay separated when a duplicate line is removed. Neither spatial agreement nor agreement between extractors proves complete native representation.

Native-bearing PDFs therefore remain partial: Poppler can silently omit off-page text or collapse overprinted text. ## Comparison and runtime-provenance changes

Comparisons retain object-level changes and expose finding-group deltas with before/after recognizer-match counts. Groups use entity type, classification, detection reason and segment. `finding_summary` counts groups; it does not count unique values, patients or example snippets. Detection reasons and segment metadata are read for comparison, but matching-value evidence and excerpts are not loaded. A value can change while its group/count remains unchanged.

Finding deltas require completed scans of the same source, complete baseline/current object reads, matching detector/policy and known processing-runtime provenance. Newly inventoried objects additionally require no baseline coverage gaps before their finding changes can be attributed. Incomplete or sampled reads, access loss, changed detector/policy and unknown provenance leave finding changes unknown; they never establish removal. Legacy scans without recorded runtime identity need a new baseline. Changing evidence capture alone does not make otherwise comparable scans incomparable. The dashboard distinguishes object counts from finding changes and displays the reason when finding changes are unknown.

The bundle generator hashes a versioned description of immutable API/Tika image IDs, writes `runtime_identity` in `release.json` and stamps `DISCOVERY_RUNTIME_ID` on API and worker through the generated image/platform override. API or Tika changes alter the identity; web/catalog-only changes do not. Detector versions separately include pipeline/model details. Local native-only runs without a parser URL or supplied bundle identity record a package-name/version inventory hash. External-parser runs without a valid recorded identity are unverified. These are recorded deployment/version facts, not remote attestation of an arbitrary parser or proof that a manually copied identity describes the running software. Keep the supplied images and override together, and never reuse the marker for an altered external parser.

The regression cases are in `backend/tests/test_comparison.py`, `backend/tests/test_provenance.py`, `scripts/test_bundle.py` and the frontend comparison helper tests. They cover source-to-finding comparisons, coverage/policy/runtime gates, aggregate group counts, evidence omission and generated runtime stamps. The current reconciliation/evaluation changes narrow earlier implementation gaps but do not establish complete native-PDF representation or hospital patient-linkage accuracy. Those requirements are distinct from obtaining hospital access and representative annotations.

## Behavior retained from the previous release

PostgreSQL now requires the deployment CA (`SOURCE_DATABASE_CA_FILE`) and generates a `verify-full` connection with a TLS 1.2 minimum and disabled GSS encryption. Old stored DSNs cannot preserve a weaker TLS setting when source preflight runs. API connection checks and worker scans share a lock for the same configured connector/host/port/database, across different credentials, schemas and table scopes. A busy check returns HTTP 409 and a busy worker run remains queued. Distinct aliases or catalogs are not coordinated. The implementation and regression cases are in `backend/tests/test_postgresql_security.py` and `backend/tests/test_source_locks.py`. The refreshed [PostgreSQL report](../fixtures/evaluation/postgres-integration.json) records 17 passing synthetic checks, including wrong-name/untrusted certificate rejection, grant/timeout/cancellation controls, cross-account lock contention, separate-database concurrency and lock release after failure.

Native JSON/JSONL/XML extraction and structured database cells now preserve sibling/nested records, including serialized payloads. They do not carry an outer patient identifier into nested records. Invalid/duplicate-key/unsafe or limited structured input yields partial coverage; explicit Patient Name headers also separate text records. Detection, extraction and scanning tests include original synthetic files, native/string JSON database cells, own-record positive links, cross-record negatives and excerpt boundaries. ABHA underscore labels and diagnosis-code field context are covered. These tests do not establish semantic linkage accuracy on arbitrary hospital layouts.

Approved retention is checked independently of scanning approximately every 30 seconds, using bounded cleanup batches. Expired active scans lose their stored findings/objects/evidence, are cancelled, and cannot repersist expired results at checkpoints/commit; the remaining scan marker is removed after the worker releases it. Startup cleanup and failure handling are covered by `backend/tests/test_retention.py`. The behavior does not promise instant parser-memory zeroization or deletion of independent exports/backups. See the runbook for worker-down behavior and cleanup limits.

## Important limits

- The actual hospital database engine/version, identifier formats, representative volumes, read-only grants, scan windows, permitted workload and retention settings are not known. Complete the inventory and acceptance checklist before deployment.
- Hosting remains undecided. The portable deployment targets a client-controlled Linux VM on premises or in approved private cloud infrastructure; actual client installation, egress controls, volume encryption, private source connectivity and acceptance remain pending.
- PostgreSQL, MySQL and SQL Server adapters are implemented. Other HIS engines need a dedicated, tested adapter. Live SMB authentication and hospital network access still need acceptance against the approved server.
- Supported images can be full only after every original frame is processed without limits and no uninspected nonvisual metadata remains. Native-bearing PDFs stay partial despite spatial reconciliation because original native representation is unverified. Only eligible blank/raw-pixel image-only PDFs can pass every zero-native-operation, ancillary, geometry and processing gate. Encoded-image metadata and Office/Tika-only extraction remain partial. No processing status establishes OCR recognition accuracy.
- Detector scores are heuristic recognizer scores, not calibrated probabilities. Match counts can include repeated OCR/native-text observations and are not unique patient counts.
- Finding-group comparison counts are aggregate recognizer observations, not individual matching-value changes. Legacy/unknown processing-runtime provenance requires a new baseline; a copied deployment marker cannot attest an altered parser.
- Version-2 evaluation measures exact value occurrences within source objects. Version 3 adds clinical presence and exact patient-reference association by supported original record; arbitrary PDF/OCR/Office mappings, semantic diagnosis accuracy, original PII spans and schema-only PII occurrence classes remain unsupported. The tiny synthetic fixture sets cannot establish Indian-name performance or the 95% hospital targets. A candidate flag never sets `hospital_validated` or closes unresolved PDF/PHI requirements.
- The base deployment is isolated for mounted-file scanning. Routed database/SMB/private cloud access requires hospital-provisioned firewall rules and a separate positive/negative reachability test. Application allowlists supplement those rules.
- Sensitive fields are encrypted by the application; full-volume encryption, encrypted backups, trusted certificates, key escrow and operating-system hardening must be provisioned locally.
